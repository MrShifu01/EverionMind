### RLS policy review (60 policies, 35 tables)

#### What's solid
- All 39 public tables have `relrowsecurity = on`.
- User-scoped tables (`user_*`, `*_integrations`, `notifications`, `idempotency_keys`, `tags`, `gmail_decisions`, `important_memories`, `vault_keys`, `user_memory`) all use the canonical pattern: `(user_id = (SELECT auth.uid()))` — performance-tuned (advisor lint 0003 *not* triggered for these).
- Brain-scoped tables (`entries`, `concept_graphs`, `knowledge_shortcuts`, `query_feedback`) check brain ownership via the cached `is_brain_owner` / `is_brain_member` helpers (no per-row recursive subqueries).
- `audit_log`: read-only for the row's owner; service-role only for inserts. Correct.
- `entry_shares`: tightly scoped — owner of source entry, brain owner, or member of target brain. Three-arm OR is intentional.
- `marketing_leads_anon_insert`: `WITH CHECK (true)` looks scary but is intentional for the email-capture form. Anon role + INSERT only; no read.

#### Findings

**[HIGH] vault_entries has duplicate-overlapping policies.** Performance advisor 0006 flags 4 of them. The looser `vault_entries_all` (just `user_id = auth.uid()`) is OR'd with the stricter `vault_entries_select/insert/update/delete` (which also require brain membership). RLS is permissive — the looser policy wins. **A vault entry where `brain_id` IS NULL or whose brain was deleted (FK is CASCADE so this can't happen, but the loose policy still admits weird rows) would be accessible without the brain-membership check.** The stricter policies are dead code today; `vault_entries_all` is the effective gate.
- **Fix:** drop `vault_entries_all` (and probably `_select` since `_all` overlaps it) — keep the four CRUD-specific policies, all of which require brain membership in addition to ownership.
- **Files:** flagged in advisor lints; see `vault_entries_all` policy definition above.

**[MEDIUM] Two tables miss the `(SELECT auth.uid())` pattern.** Performance advisor 0003 flagged:
- `gmail_pattern_rules.gmail_pattern_rules_owner_rw` — `auth.uid() = user_id` (re-evaluated per row)
- `user_enrich_quota.user_enrich_quota_owner_read` — same
Both also have `roles=-` (PUBLIC instead of `authenticated`). At current scale (3 / 0 rows) the perf is fine; at launch volume this becomes a per-row function call.
- **Fix:** rewrite both as `((SELECT auth.uid()) = user_id)` and pin role to `authenticated`.

**[LOW] concept_graphs / knowledge_shortcuts / query_feedback** scope by `brain_id IN (SELECT id FROM brains WHERE owner_id = auth.uid())` — **owner only, not members**. If shared-brain members should also see the concept graph + suggestions, this is a product gap. If owner-only is by design (concept graph is "the owner's view of what they know"), this is correct. Worth confirming with the product spec.

**[LOW] brain_invites + brain_members + audit_log** have no INSERT/UPDATE/DELETE policies for `authenticated`. Mutation goes through service-role only. Correct, but worth a comment on each table so a future contributor doesn't add a permissive policy.

`user_ai_settings.active_brain_id → SET NULL` is correct — when the active brain is deleted, the setting nulls out, not the whole row.

**[HIGH] `entries_embedding_hnsw_idx` shows 0 scans** — verify retrieval is actually using it. Migration 074 created the HNSW; if retrieval is always falling back to seq-scan, vector search is silently slow.

### Missing indexes (advisor lint 0001)

Four FK columns lack a covering index:
- `brain_invites.invited_by`
- `brain_members.invited_by`
- `brain_vault_grants.granted_by`
- `entry_shares.shared_by`

All four are `*_by` columns recording who performed the action. No queries currently filter on them, so impact is low — but if any "actions performed by user X" admin query lands, these become full table scans. **Fix:** add four `CREATE INDEX idx_*_by ON … (… _by);` statements.

### High seq-scan tables (potential missing indexes)

| Table | Rows | Seq-scans | Tuples read | Tuples-per-row |
|---|---|---|---|---|
| `entries` | 387 | 13,163 | 2,736,124 | 7,070 |

`brains` and `user_ai_settings` are tiny — Postgres planner correctly picks seq scan for them. **Expected, not a bug.**

## 6. Function security (advisor lints)

### `function_search_path_mutable` (7 hits)

Functions without `SET search_path` can be hijacked by a `pg_temp` namespace shim if an attacker ever lands code execution in another extension. Low real-world risk in this single-tenant Supabase project, but trivial to fix with `ALTER FUNCTION … SET search_path = public, pg_temp;`.

Affected:
- `create_personal_brain_for_new_user`
- `user_personas_touch_updated_at`
- `handle_new_user`
- `match_gmail_pattern`
- `important_memories_touch`
- `_lock_billing_columns`
- `enforce_entries_brain_owner_match`

### `anon_security_definer_function_executable` (16 hits)

**[MEDIUM]** 16 SECURITY DEFINER functions are callable by the `anon` role via PostgREST RPC. Most check `auth.uid()` internally and degrade gracefully; some are read-only helpers (`is_brain_member`, `is_brain_owner`, `is_entry_shared_to_user`) that the RLS policies themselves use.

The risky ones are the **mutating** SECURITY DEFINER functions: `capture`, `quick_capture`, `save_links`, `bulk_apply_embeddings`, `claim_pending_enrichments`, `consume_enrich_quota`, `recompute_enrichment_state`, `handle_new_user`. If any of these has a missing `auth.uid()` gate inside, anon can write rows.

**Fix path:**
1. Audit each of these functions for an explicit `IF auth.uid() IS NULL THEN RAISE EXCEPTION; END IF;` early return (or a `_user_id` parameter that's verified against `auth.uid()`).
2. Either:
   - **Option A**: `REVOKE EXECUTE ... FROM anon;` for mutating functions — they're called from the API layer with the service-role key, not from the browser as anon. This is the cleanest path.
   - **Option B**: switch them to `SECURITY INVOKER` so RLS applies to writes inside the function.
3. For pure read helpers used by RLS (the `is_brain_*` family), `SECURITY DEFINER` is correct — RLS itself needs the bypass to avoid recursion.

### `auth_leaked_password_protection` (1 hit)

[**LOW** — auth provider feature toggle]
HaveIBeenPwned check is disabled. Toggle on in Supabase dashboard → Auth → Password protection. One-click change.

### `rls_policy_always_true` (1 hit)

`marketing_leads_anon_insert` has `WITH CHECK (true)`. Intentional — anonymous email capture for marketing. **Mitigation:** API layer rate-limits this endpoint. Worth a `COMMENT ON POLICY` documenting the intent.

## 9. Recommended migration plan

Three small migrations + two dashboard toggles. Total effort: ~1 hour.

### Migration 083 — RLS hardening pass

```sql
-- F1: drop overlapping vault_entries policy (the strict ones cover all CRUD)
DROP POLICY IF EXISTS vault_entries_all ON public.vault_entries;

-- F3: rewrite two PUBLIC-scoped policies with the perf-tuned (SELECT auth.uid()) pattern
DROP POLICY IF EXISTS gmail_pattern_rules_owner_rw ON public.gmail_pattern_rules;
CREATE POLICY gmail_pattern_rules_owner_rw ON public.gmail_pattern_rules
  FOR ALL TO authenticated
  USING ((SELECT auth.uid()) = user_id)
  WITH CHECK ((SELECT auth.uid()) = user_id);

DROP POLICY IF EXISTS user_enrich_quota_owner_read ON public.user_enrich_quota;
CREATE POLICY user_enrich_quota_owner_read ON public.user_enrich_quota
  FOR SELECT TO authenticated
  USING ((SELECT auth.uid()) = user_id);

-- F6: pin search_path on the 7 affected functions
ALTER FUNCTION public.create_personal_brain_for_new_user() SET search_path = public, pg_temp;
ALTER FUNCTION public.user_personas_touch_updated_at() SET search_path = public, pg_temp;
ALTER FUNCTION public.handle_new_user() SET search_path = public, pg_temp;
ALTER FUNCTION public.match_gmail_pattern(...) SET search_path = public, pg_temp;
ALTER FUNCTION public.important_memories_touch() SET search_path = public, pg_temp;
ALTER FUNCTION public._lock_billing_columns() SET search_path = public, pg_temp;
ALTER FUNCTION public.enforce_entries_brain_owner_match() SET search_path = public, pg_temp;

-- F8: document FK intent so a future contributor doesn't switch to CASCADE
COMMENT ON CONSTRAINT entries_brain_id_fkey ON public.entries IS
  'NO ACTION on purpose — brain delete must hard-delete or migrate entries first.';
COMMENT ON CONSTRAINT links_brain_id_fkey ON public.links IS
  'NO ACTION mirrors entries — brain delete cleans up entries which cascade-clean links.';
```
